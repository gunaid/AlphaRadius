# كروت User Manager 6 المستخدمة واسم المجموعة في الباقات (27 نوفمبر 2026)

## المشكلة

User Manager 6 لا يعطي عبر API تاريخ أول استخدام الكرت ولا تاريخ انتهائه (الحقول `till-time` و`first-used` غير موجودة؛ المتاح: البروفايل الحالي والوقت والتحميل والرفع المستخدمة). المستورد يرفض تخمين التواريخ، فكانت كل الكروت المستخدمة تذهب إلى «يحتاج مراجعة» ولا تُستورد (2,125 كرتًا في حالة المستخدم)، فلا يستطيع أصحابها الدخول بعد التحويل.

## الخيار الجديد (قرار المشغل)

في صفحتي الاستيراد، قائمة «استهلاك وسجلات الكروت السابقة» فيها خيار ثالث:
**«الكروت المستخدمة: الرصيد المتبقي، والصلاحية من تاريخ الاستيراد»** (`used_cards_mode=restart`). الافتراضي بلا تغيير (`review`).

لكل كرت عليه استهلاك في User Manager:

* **الرصيد المتبقي من المصدر:** استهلاكه (رفع، تحميل، وقت) يُحفظ كسطر محاسبة واحد مجمّع (`Consolidated-Historical-Import`) عند بداية الدورة، فالمتبقي = حدود الباقة ناقص الاستهلاك.
* **الصلاحية من الاستيراد:** `first_used_at` و`last_renewed_at` = لحظة الاستيراد (ثوانٍ كاملة)، و`expires_at` = لحظة الاستيراد + صلاحية الباقة. صاحب الكرت يحصل على أيام إضافية، لكن البيانات والوقت محسوبان بدقة.
* **كل حد يُفحص منفردًا:** يكون الكرت `expired` فقط إذا استُهلكت بياناته أو وقته بالكامل؛ المعطل في User Manager يبقى معطلًا.
* **جلسة مفتوحة وقت الاستيراد** (الراوتر يرسل محاسبة جلسات User Manager إلى الخادم): يُسجّل لها baseline عند بداية الدورة، فتُحسب زيادتها بعد الاستيراد فقط ولا يُرفض الكرت برسالة التسوية.
* الكروت غير المستخدمة تبقى جديدة كما كانت، والكروت الموجودة مسبقًا تُتخطى (اختر «تخطي»).
* الاستيراد قابل للتراجع كالمعتاد، بما في ذلك الـ baselines. الحساب الذي تغيّر بعد الاستيراد (دخل وصرف) يبقى للمراجعة ولا يُحذف.

**التوقيت:** استهلاك User Manager يتغير ما دام يعمل؛ استورد الكروت المستخدمة مباشرة قبل تحويل الراوتر إلى هذا الخادم، في وقت هادئ.

## كلمة المرور المخفية `*****`

عندما لا يملك مستخدم API في الراوتر صلاحية `sensitive`، يعيد RouterOS كلمة مرور كل مستخدم بالشكل `*****` بدل قيمتها. كان المستورد يحفظها كلمة مرور حقيقية، فرُفض دخول كل الكروت المستوردة (الصفحة ترسل رقم الكرت فقط). الآن أي كلمة مرور من نجوم فقط تعامل كفارغة: كلمة المرور = رقم الكرت (كروت الرمز الواحد)، وتعرض نتيجة الاستيراد عددها. كلمة مرور حقيقية فيها نجمة مع أحرف أخرى تبقى كما هي.

إصلاح الكروت المستوردة قبل هذا التعديل (مجرب على قاعدة المختبر؛ لا يغير إلا كلمة المرور وPIN؛ مشغل التفعيل الأول يبقي لقطات الكروت غير المستخدمة فارغة كما عند الإدخال):

```
START TRANSACTION;
UPDATE radcheck r JOIN wisp_vouchers v ON v.username=r.username SET r.value=v.username
 WHERE r.attribute='Cleartext-Password' AND r.value REGEXP '^[*]+$';
UPDATE wisp_vouchers SET password=username, pin_code=LEFT(username,32) WHERE password REGEXP '^[*]+$';
COMMIT;
```

## اسم المجموعة (MikroTik group)

* يُقرأ `group-name` من Limitations في User Manager (من API ومن ملف التصدير) ويُربط بالبروفايل.
* الباقة الجديدة تُنشأ بهذه المجموعة (`wisp_packages.mikrotik_group`)، ويُضاف لها `Mikrotik-Group` في `radgroupreply` فيأخذ المستخدم بروفايل الهوتسبوت نفسه.
* باقة موجودة **مجموعتها فارغة** تُملأ من User Manager (مسجّلة في سجل الاستيراد وتُعاد عند التراجع). مجموعة محددة مسبقًا لا تُستبدل أبدًا.
* لقطة الكرت `snap_mikrotik_group` = مجموعة باقته (كانت ثابتة `ALL-SPEED`).
* وُحّد اسم حزم الاستيراد في كل الدفعات: «استيراد يوزرمانجر - الباقة».

## الفحوص

* `tests/test_userman_used_cards.py` (معزول، 8): حالة الكرت، كل حد منفردًا، وحدات الصلاحية، مصادر الاستهلاك، تنظيف اسم المجموعة، والتوصيل بالصفحتين والخدمة.
* `tests/run_userman_used_cards_lab.py --run` (MariaDB `userman_used_lab`، 6؛ منها كلمة المرور المخفية): الاستيراد الفعلي بـ `execute_userman_import`، ثم **استعلام Core الحقيقي** `authorize_check_query` من `queries.conf`: كرت 235/300MB و5h25m/7h يُقبل، كرت بجلسة مفتوحة لا يُرفض بالتسوية، المستهلك بالكامل يُرفض، وبعد 70MB إضافية يظهر رفض الحصة. المجموعة تصل للباقة والكرت وradgroupreply، وتُملأ للباقة الفارغة مرة واحدة ولا تُستبدل، والتراجع يزيل كل شيء عدا الحساب الذي تغيّر.
* مجموعة اختبارات المستورد الحالية على MariaDB (16 حالة) نجحت مع التغيير (مع تعطيل فحص الترخيص في الغلاف فقط، لأن المختبر الحالي يسبق حماية الاستيراد بالترخيص).
* لم يُجرب على راوتر User Manager فعلي.
