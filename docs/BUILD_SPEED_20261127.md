# تسريع بناء الصور عند التحديث (27 نوفمبر 2026)

## 1. ترتيب طبقات صورة Core (`docker/freeradius/Dockerfile`)

**قبل:** مرحلة تصريف `rlm_detail` كانت تُبنى فوق المرحلة التي نسخت ملفات الإعدادات (`entrypoint.sh` والسياسات وqueries). أي تعديل إعدادات كان يعيد تثبيت gcc ومكتبات التطوير وتنزيل كود FreeRADIUS المصدري وتصريف الوحدة.

**بعد:** ثلاث مراحل: `radius-base` (الحزم فقط)، `detail-build` فوقها، والصورة النهائية فوقها تنسخ الوحدة المصرفة ثم ملفات الإعدادات. تعديل الإعدادات يعيد خطوات النسخ الأخيرة فقط (ثوانٍ، دون تنزيل).

**الفحص:** BuildKit حقيقي بنفس Dockerfile القديم والجديد، مع استبدال خطوتي apt وخطوة التصريف بخطوات بديلة تنتج نفس الملفات (لأن مرايا Debian غير متاحة من بيئة الاختبار)، ثم تعديل `entrypoint.sh` وإعادة البناء:

| | القديم | الجديد |
|---|---|---|
| تثبيت أدوات التصريف | يُعاد | مخزن (CACHED) |
| تصريف rlm_detail | يُعاد | مخزن |
| نسخ ملفات الإعدادات | يُعاد | يُعاد |

والصورة النهائية القديمة والجديدة متطابقة: نفس Entrypoint وWorkingDir والمنافذ والمتغيرات، ونفس الملفات التسعة (المحتوى والصلاحيات). لم يُبنَ Core بحزم Debian الحقيقية في بيئة الاختبار.

## 2. التصريف المتوازي في صورة Web (`packaging/compile_runtime.py`)

**قبل:** كل وحدات Python (حوالي 200) تُصرّف إلى C ثم بـ gcc واحدة تلو الأخرى (`nthreads=1`، `--parallel 1`)، فهي أطول خطوة في كل تحديث للويب.

**بعد:** عدد العمليات = عدد المعالجات، بحد أقصى 8، وبحد 1GB تقريبًا من الذاكرة المتاحة لكل عملية (حتى لا تنفد ذاكرة جهاز صغير). يطبع السكربت العدد المستخدم. للتحكم يدويًا: `--build-arg ALPHA_COMPILE_JOBS=2` في `docker build` (أو `1` للسلوك القديم). نفس الوحدات ونفس خيارات Cython وgcc؛ تغيّر الترتيب الزمني فقط.

**الفحص:** `tests/test_build_speed.py` (معزول، 5)، وقياس فعلي بتصريف نسخة من الكود بنفس إصدارات Cython 3.1.4 وsetuptools 80.9.0 (القيم في قسم النتيجة أدناه).
